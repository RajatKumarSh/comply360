# ADR-008: Compliance State and Assets

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-09-27 |

## Context

Compliance must distinguish:

- Historical audit result: "What was true during the audit?"
- Current compliance state: "What is true now?"

Domain Model v0.1 did not define what a compliance "item" is. It also did not define how asset changes relate to compliance updates, which risked the same fact being entered twice.

## Decision

### Compliance state

- `compliance_state` has one row per **workshop × requirement** (ADR-003), holding the current status, when it last changed, and the update that changed it.
- `compliance_state` changes **only** through `compliance_update` rows.

### Compliance update

`compliance_update` is append-only (ADR-007):

- Workshop
- Requirement
- Previous status
- New status
- Source
- Actor
- Timestamp
- Reason
- Remarks
- Evidence

Sources:

| Source | Meaning |
|---|---|
| `AUDIT_BASELINE` | Written when an audit is finalized, for each requirement-linked question. |
| `MANUAL_UPDATE` | A user records a change with reason and evidence. |
| `ASSET_EVENT` | Generated by an asset status change on an asset-linked requirement. |
| `LEGACY_BASELINE` | Initial state recorded for a legacy workshop without audit history. |

### Audits

Finalizing an audit writes an `AUDIT_BASELINE` compliance update for each question linked to a requirement. The audit and its responses are never modified.

### Superseding audits

When a superseding audit (ADR-006) is finalized:

- New `AUDIT_BASELINE` compliance updates are generated from the superseding audit.
- Compliance updates generated by the original audit remain in history.
- The original audit is not rewritten or deleted.

### Assets

For a requirement linked to an asset type, an asset status event (for example `INSTALLED`) creates the compliance update **in the same transaction**. Assets are entered once; compliance follows.

The mapping from asset status to compliance status is configuration. Its values are not yet defined.

### Reading compliance

| Question | Source |
|---|---|
| What was true during the audit? | The finalized audit's responses |
| What is true now? | `compliance_state` |
| What was true on date X? | `compliance_update` history |

## Consequences

- Historical audits and current compliance are both always available.
- No double entry between assets and compliance.
- Compliance reporting is consistent per requirement.

## Deferred / Open

- Compliance status values (for example Available / Not Available / Partial) (before the compliance phase).
- Asset status → compliance status mapping (before the compliance phase).
- Commercial support eligibility based on compliance (later phase).
